FirewallGuard AI

Multi-tenant SaaS platform for SonicWall firewall security posture analysis

Version — Production (All 4 Phases) Stack — FastAPI · React · PostgreSQL · Celery Date — July 2026

1. System Overview

FirewallGuard AI is a multi-tenant SaaS platform that ingests SonicWall Tech Support Reports (TSRs), evaluates them against a detection rule catalog, correlates attack paths, matches firmware against the PSIRT advisory database, and scores each device's security posture. Findings flow into a workflow system with triage, alerting, and ticketing integrations.

3. Analysis Engine (firewallguard/)

The analysis engine is standalone and database-agnostic — it processes raw TSR text and returns a plain JSON-serializable dict. It has no awareness of organizations, users, or the HTTP layer.

6. Hybrid Rule Engine

The rule engine has two tiers that are merged transparently before findings are returned to the API:

System Rules (~67)

Python callables in firewallguard/rules/catalog*.py. Authoritative, evidence-gated, rich per-object findings. Mirrored into the DB by seed_system_rules() so the admin GUI can list them — but they cannot be edited by tenants.

Custom Rules (CEL)

Tenant-authored expressions evaluated by app/rule_engine.py. Require CEL syntax, go through Draft → Submitted → Approved workflow. Run against the same snapshot as system rules.

Suppressions — tenant-wide or device-wide overrides applied after pipeline evaluation. Can disable a rule or override its severity. Stored in RuleSuppression with optional expiry date.

Firmware compliance — admin-configured DeviceGeneration + FirmwareRecommendation mappings; check_firmware_compliance() emits a Critical finding for unsupported or outdated firmware.

10.3 Snapshot-Based Findings

The result_json field in the Analysis table stores the complete pipeline output snapshot as a JSON dict. When a user selects an older TSR in the findings explorer, the frontend fetches GET /analyses/{id}/findings which reads from that snapshot — findings appear exactly as they were at analysis time. Live triage state (status, assignee, comments) is fetched separately from the findings workflow table and merged on the client.

11. Authentication & Multi-Tenancy

11.1 Authentication Methods

Password (JWT)

  • bcrypt hashing (pinned 4.0.1)
  • Access token: 60-min TTL (HS256)
  • Refresh token: 14-day TTL, rotated on use
  • Lockout: 5 failed attempts → 15-min block

MFA (TOTP)

  • RFC 6238 TOTP (6-digit, 30-second window)
  • QR code enrollment via mfa.py
  • Short-lived MFA token (5-min) between password and OTP steps
  • bcrypt-hashed single-use backup codes

SSO (OIDC / SAML)

  • OIDC: JWKS-verified — Okta, Microsoft Entra, Google
  • JIT user provisioning on first login
  • Group claim → org role mapping
  • Tokens returned via #/sso?access=…&refresh=… fragment
  • SAML 2.0 supported (sig validation not enforced; OIDC is production path)

API Tokens

  • Format: fgat_<random> (prefix for log filtering)
  • bcrypt hash stored; plaintext shown only once
  • Scoped + expiry configurable
  • Resolve to a transient service-principal User scoped to the token's org

11.2 Tenant Isolation

Every API endpoint extracts organization_id from the JWT payload — never from request parameters. All database queries are filtered by WHERE organization_id = user.organization_id. Cross-org access returns 404 (not 403, to avoid information leakage).

11.3 RBAC Roles

RoleRankCapabilities
Owner4Full control including billing, org deletion, all below

11.4 MSP Multi-Tenancy

An Organization with is_msp = true owns many Customer rows (managed clients). Each Device belongs to a Customer. The MSP frontend shows a customer list; selecting a customer scopes all device/finding views to that customer's data.

11.5 Superadmin (Cross-Tenant Operator)

User.is_superadmin is set only out-of-band during bootstrap (--superadmin flag). It grants access to /platform/* (cross-tenant overview), /tsr-tester, and /api-config. It is never exposed through the tenant-facing API and can never be set by API-token principals.

15. Key Design Decisions

DB-Agnostic Analysis Engine

The firewallguard/ package has zero dependency on SQLAlchemy or the HTTP layer. The pipeline returns a plain JSON-serializable dict — stored in result_json and reloadable at any time. This enables standalone CLI use, easy testing, and snapshot-based historical findings.

Dual-Format TSR Normalization

GUI and SonicOS API TSRs look completely different at the byte level. The normalizer detects format and rewrites API TSRs to GUI-equivalent text — one code path, one rule set, verified parity (identical findings, scores, and severity counts).

Hybrid Rule Engine

System rules (Python) are authoritative and run unconditionally. Custom rules (CEL) are layered on top. Suppressions are applied last. This separation keeps the core rule set stable while allowing per-tenant customization without code changes.

JWT Tenant Isolation

organization_id lives in the JWT payload, set at login. No endpoint accepts it as a query param. Cross-org access returns 404 — not 403 — to avoid resource enumeration.

Finding Fingerprinting

Fingerprint = rule_id + object_name + object_type. Enables auto-reopen (rule fires again after fix), auto-resolve (rule no longer fires), and drift detection across scans — all handled transparently by sync_findings().

Configurable API Flow

The SonicOS API workflow (login URL, auth type, TSR export path, success conditions) is editable from the superadmin UI without code changes. Templated steps support {{ip}}, {{username}}, and extracted variables. Per-step tracing (URL, status, body, time) with auth header redaction.

Hash-Based SPA Routing

All routes use URL hashes (#/devices, #/findings/123). The entire frontend deploys as static files with no server-side routing configuration — Nginx serves index.html for every request and the client handles the rest.

License-Driven Scan Frequency

Plans define analysis_frequency (monthly / weekly / daily / hourly). Devices inherit frequency at registration. Schedules are enforced at the API layer by enforce_analysis_frequency(). Redis slot management prevents concurrent scan overload per org.

Security Controls Summary

  • Passwords — bcrypt (pinned 4.0.1 for passlib compatibility)
  • Secrets — Fernet encryption for device credentials and integration configs
  • Tokens — JWT HS256; API tokens bcrypt-hashed; prefix fgat_ for log filtering
  • Headers — HSTS, CSP, X-Frame-Options, X-Content-Type-Options
  • Rate limiting — Per-IP fixed-window middleware
  • Audit — Append-only log; no deletes; captures all privileged actions
  • Lockout — 5 failed logins → 15-minute account lock
  • PSIRT — Daily advisory refresh; Critical finding for affected firmware
  • SBOM — CycloneDX sbom.json generated by cyclonedx-bom
